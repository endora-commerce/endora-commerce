# Feature Specification: Declared extension columns on core tables (S2)

**Feature Branch**: `spec/178-extensible-columns`
**Created**: 2026-11-10
**Status**: Approved (D-291, 2026-11-10); Phases A – C in implementation (US3 waits for spec 176)
**Input**: Owner rulings of 2026-11-10 on the instance-extensibility review: OD-13 (b), OD-14 (a),

## Context

Measured on `origin/master` at `2cc56ea9b`:

- An instance customises through installed module packages. A package may ship its own entities
  and migrations (`packages/platform/src/packages/package-runtime.ts`,
  `packageSchemaContributionsUnder`), and nothing reads what those migrations do to another
  module's table. A raw `alter table organizations add column …` in a package migration is
  accepted, unrecorded and unverifiable after an upgrade.
- MikroORM 6.6.16 refuses two entities on one table by default (`checkDuplicateTableNames`), and
  the platform passes no `discovery` options (`packages/platform/src/db/mikro-orm.config.ts`).
- Nine host tables carry custom fields today
  (`packages/modules/custom_fields/src/backend/services/host-storage-binding.ts`): `organizations`,
  `customer_accounts`, `orders`, `quote_requests`, `products` (its value bag is the
  `products.attribute_values` **column**, so the extensible table is `products` itself),
  `categories`, `crm_opportunities`, `projects`, `tasks`. `products` carries two stored generated
  columns computed from `name` and `sku` (`packages/modules/catalog/src/backend/entities/product.entity.ts`
  l. 241–246) which `catalog` migrations drop and re-create.
- The only per-tenant guards that apply to a second mapping of a table are the ones its metadata
  carries. Measured in the spike (research R-2): a class decorated with `@OrgScoped()` and then
  used as an `EntitySchema` **loses** the filter; the filter must be declared on the schema.

The customer need behind it: "an instance adds an ERP code column on `organizations`", read and
written by the instance's ERP integration, visible next to the organization in the admin, and kept
safe across platform upgrades.

## Owner rulings *(binding; recorded 2026-11-10, not to be reopened by this feature)*

- **OR-1 (OD-13 b)** — Declared additive columns on owner-opted-in core tables; DDL generated by the
  platform from a declaration, recorded in a `schema_extensions` ledger, checked by a verifier.
  Raw cross-module migrations guarded only by a dependency are rejected.
- **OR-2 (OD-14 a)** — The ORM sees extension columns only through an extension-owned projection
  (PK + `x_<module>_*` columns on the same table). Core entity classes never get the fields.
- **OR-3 (OD-15)** — Extensible = every custom-field host table, derived from the custom-field
  binding registry rather than a second declaration.
- **OR-4 (OD-16)** — The extending module owns its `x_<moduleId>_*` columns; only its code writes
  them. Constitution I is amended accordingly.
- **OR-5 (OD-17)** — In the release that ships S2, foreign DDL/DML from package migrations on
  another module's table is refused, not warned.
- **OR-6 (OD-29)** — Uninstalling the declaring module keeps its columns (ledger marks them
  orphaned); an explicit audited command drops them. Uninstalling a host is blocked by the declared
  dependency (`dependents-block`).
- **OR-7** — Writes atomic with a core write go through a spec 176 `beforeCommit` hook in the same
  transaction, one audit entry (which, per D-288 / `specs/conventions/audit-state.md` and 176, holds
  the changed field **names**, never values).

## Clarifications

### Session 2026-11-10 (architect, no owner questions asked)

- Q: Does the generated DDL run *after* or at the *head* of the declaring module's migration block?
  → A: At the head (research R-5). The brief says "right after the declaring module's block"; the
  intent — after the host and everything the module depends on — is kept, and the head position is
  what lets the module's own later migrations back-fill the new column on a fresh database. Flagged
  as OD-178-1; the owner confirmed the head position on 2026-11-10 (D-291, *Decisions* below).
- Q: Where does an instance package declare its extension? → A: As a code export
  (`schemaExtensions`) of its `./backend` subpath, beside `entities`; not a manifest field
  (research R-7).
- Q: Which exposure points ship in 178? → A: The typed accessor, extension attributes on admin
  **reads** (detail + list) of every extensible host, and the existing admin detail zones as the UI
  slot (no new mechanism). Deferred, explicitly: `filterable`/`sortable` list flags, extension
  input on core write contracts, search/export/PDF/storefront exposure, events (FR-060 – FR-065).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — An instance declares an ERP code column on organizations (Priority: P1)

An instance developer writes a module package `acme_erp` that depends on `organizations` and
exports a `defineColumnExtension({ host: 'organizations', module: 'acme_erp', columns: { erpCode:
{ type: 'varchar', length: 64, nullable: true, index: 'unique' }, creditTier: { type: 'smallint', default: 0 } }
})`. After `pnpm install` and `migrate`, `organizations` carries `x_acme_erp_erp_code` and
`x_acme_erp_credit_tier`, a unique partial index on the first, and the ledger records three
elements. The core `Organization` entity, its responses and its audit entries are unchanged.

**Why this priority**: It is the customer case and the minimum that proves the mechanism.

**Independent Test**: The worked example fixture package (`quickstart.md`) installed into a
throwaway instance root; `migrate` then `information_schema` and the ledger are asserted; a core
organization create/read round-trip is byte-identical with and without the package.

**Acceptance Scenarios**:

1. **Given** a fresh database and the package installed, **When** `migrate up` runs, **Then** the
   two columns and the index exist, the ledger has three `applied` rows, and the generated step ran
   after every `organizations` migration and before every `acme_erp` migration.
2. **Given** a declaration with `creditTier: { type: 'smallint' }` (NOT NULL, no default), **When**
   the platform boots or migrates, **Then** it refuses with `schema_extension_invalid` naming the
   module, the key and the rule, and nothing is applied.
3. **Given** the package declares `host: 'invoices'`, **When** discovered, **Then** it is refused
   as not extensible, listing the extensible hosts.
4. **Given** the package does not declare `organizations` in its dependency closure, **When**
   discovered, **Then** it is refused (`host-not-a-dependency`).
5. **Given** the database is migrated and the package unchanged, **When** `migrate up` runs again,
   **Then** no generated step is pending and nothing changes.

### User Story 2 — Instance code reads and writes its columns (Priority: P1)

The ERP sync worker runs a Command `acme_erp.organization.sync` that calls
`extensionColumns(acmeOrganizationColumns, ctx.em).set(id, { erpCode: 'ERP-42' })`; an admin page of
the package reads `load(ids)` in bulk.

**Independent Test**: Integration test over the fixture: set in a Command → exactly one UPDATE
touching only `x_acme_erp_erp_code`, one audit entry naming the changed key, no INSERT ever.

**Acceptance Scenarios**:

1. **Given** an existing organization, **When** `set(id, { erpCode })` runs inside a Command,
   **Then** one `update "organizations" set "x_acme_erp_erp_code" = $1 where "id" = $2` is issued
   and the Command's single audit entry records `extensions.acme_erp.changedFields = ['erpCode']`
   and no value.
2. **Given** an unknown id, **When** `set` runs, **Then** it throws `ExtensionHostRowNotFoundError`
   and inserts nothing.
3. **Given** `set` is called outside a transaction (no Command, no hook), **Then** it throws
   `ExtensionWriteOutsideCommandError`.
4. **Given** `acme_erp` is switched off, **When** any accessor method runs, **Then** it throws
   `ModuleDisabledError` (fail closed) and the columns keep their values.
5. **Given** an `@OrgScoped` host (`orders`) and an actor scoped to organization A, **When**
   `load([idOfOrderInB])` runs, **Then** the result has no entry for it.

### User Story 3 — Atomic write with the core row through a command hook (Priority: P2)

On `organization.create` the package's `beforeCommit` hook sets `onboardedVia = 'admin'` in the same
transaction; a hook failure rolls back the organization too.

**Independent Test**: Integration over the fixture with spec 176 merged; a throwing hook leaves no
organization row and no audit row.

**Acceptance Scenarios**:

1. **Given** the hook registered, **When** an operator creates an organization, **Then** the row
   has `x_acme_erp_onboarded_via = 'admin'` and the single audit entry of `organization.create`
   carries `extensions.acme_erp.changedFields = ['onboardedVia']` in its after-state.
3. **Given** the standard hook `columnExtensionHook` on `organization.admin_patch` and a server-side
   caller passing `extensions: { acme_erp: { erpCode: 'ERP-7' } }` to the Command, **Then** the
   column is written in the same transaction; an invalid value answers 422
   `SCHEMA_EXTENSION_INPUT_INVALID`.
2. **Given** the hook throws, **Then** neither the organization nor any audit entry exists.

### User Story 4 — Operator sees extension attributes on admin reads (Priority: P2)

The package's admin zone on the organization detail screen calls
`GET /api/v1/admin/organizations/:id?extensions=acme_erp` and receives
`data.extensions.acme_erp = { erpCode, creditTier, onboardedVia }`.

**Acceptance Scenarios**:

1. **Given** the declaration sets `adminReads: true`, **When** the request names `acme_erp`,
   **Then** the response carries `extensions.acme_erp`; without the parameter, the response is
   byte-identical to today's.
2. **Given** the module is off, uninstalled or declares no `adminReads`, **When** named, **Then**
   the key is silently absent (off behaves as never installed).
3. **Given** a list request of 50 organizations naming `acme_erp`, **Then** the extension values are
   loaded with exactly one additional query.

### User Story 5 — Upgrades cannot silently lose extension columns (Priority: P1)

**Acceptance Scenarios**:

1. **Given** a core release whose migration rebuilds `organizations` without the `x_*` columns,
   **When** core CI runs, **Then** the preservation test fails naming the table and the migration.
2. **Given** an instance database where a column was dropped by hand, **When** the backend boots,
   **Then** boot fails naming the module, the column, the table and the last executed migration of
   the table's owning module.
3. **Given** `migrate up` applies a core migration that loses a declared column, **Then** the whole
   run rolls back (the verifier runs inside the migration transaction).

### User Story 6 — Uninstall keeps data; dropping is explicit (Priority: P2)

**Acceptance Scenarios**:

1. **Given** `module:uninstall acme_erp --hard`, **Then** the columns and their values remain and
   the ledger rows are `orphaned`.
2. **Given** orphaned rows, **When** the operator runs
   `module:schema-extensions drop acme_erp --confirm`, **Then** the columns and index are dropped,
   rows become `dropped`, and one audit entry `schema_extension.drop` records what was dropped.
3. **Given** `acme_erp` is installed, **When** `module:uninstall organizations` runs, **Then** it is
   refused with `dependents-block` naming `acme_erp`.
4. **Given** `acme_erp` is installed and declares the column, **When** drop is requested, **Then**
   it is refused (`extension-still-declared`).

### User Story 7 — Package migrations cannot write other modules' tables (Priority: P1)

**Acceptance Scenarios**:

1. **Given** an installed package whose migration runs `alter table organizations add column foo`,
   **When** `migrate up` runs, **Then** it is refused with `foreign-schema-write` naming the package,
   migration and table, and the run rolls back.
2. **Given** the declaring module's own migration runs
   `update organizations set x_acme_erp_credit_tier = 1 where tax_id like 'PL%'`, **Then** it is
   allowed (own columns, back-fill).
3. **Given** the same migration sets `name = …`, **Then** it is refused.

### Edge Cases

- Two modules extend one table: independent prefixes, independent ledger rows, independent
  projections; ordering between them is irrelevant.
- A declaration removes a key: its column is marked `orphaned`, not dropped; re-adding the same key
  with the same spec re-attaches it; with a different spec it is refused.
- A declaration changes a key's type, nullability or default: refused (`non-additive-change`);
  declare a new key.
- A column name over 63 bytes: refused at declaration.
- `x_<module>_` column already on the table but not in the ledger: adopted if its type matches the
  declaration, refused otherwise.
- `db:fresh`: drops the schema, so the ledger and columns are rebuilt from declarations.
- The host module is hard-uninstalled after the extension was hard-uninstalled: the host's table
  drop takes the orphaned columns; the ledger rows become `dropped` (FR-034).
- `products` generated columns: additive columns do not touch them; the preservation test covers
  `catalog`'s drop-and-recreate of the generated columns.

## Requirements *(mandatory)*

### Declaration

- **FR-001**: The platform MUST publish `defineColumnExtension(decl)` on
  `@endora-commerce/platform/kernel`, returning a frozen, typed declaration whose value types are
  inferred from the column specs (`ColumnExtensionValues<D>`, `ColumnExtensionPatch<D>`).
- **FR-002**: The platform MUST publish `columnExtensionSchema(decl)` and
  `columnExtensionPatchSchema(decl)` returning Zod schemas equivalent to the inferred types.
- **FR-003**: Column types MUST be one of `text`, `varchar` (with `length` 1–1024), `boolean`,
  `smallint`, `integer`, `bigint`, `numeric` (with `precision` 1–38, `scale` 0–precision), `date`,
  `timestamptz`, `uuid`, `jsonb` (with a required Zod `schema`). Anything else is refused.
- **FR-004**: A column MUST be nullable or carry a constant `default` of its type; NOT NULL without
  a default is refused. `timestamptz` and `jsonb` columns MUST be nullable.
- **FR-005**: `index: true` creates a non-unique btree index on the column; `index: 'unique'`
  creates a unique partial index `where <col> is not null` and is allowed only on nullable columns.
  `jsonb` columns may not be indexed. No index, constraint, trigger or foreign key may reference a
  core column.
- **FR-006**: Physical names MUST be `x_<moduleId>_<snake_case(key)>`; keys match
  `^[a-z][a-zA-Z0-9]*$`; a name over 63 bytes is refused; index names follow
  `contracts/generated-ddl-and-ledger.md` §2.
- **FR-007**: A declaration MUST be refused when its `module` is not the declaring package's
  `endora.id`, when its host is not extensible (FR-010), when the host's owning module is not in
  the declaring module's dependency closure, when two declarations share `(module, host)`, or when
  it declares more than 32 columns.
- **FR-008**: An installed package declares extensions by exporting `schemaExtensions` (an array of
  declarations) from its `./backend` subpath; `packageSchemaContributionsUnder` reads it. Workspace
  module packages of this repository MUST NOT declare extensions (refused by the composer).

### Extensible hosts

- **FR-010**: The extensible host list MUST be derived from one custom-field host binding registry
  published in `@endora-commerce/contracts` (table, value column, owning module per
  `SupportedEntityType`), which `custom_fields`' `hostStorageBinding` also reads. No second list.
- **FR-011**: A temporary platform rollout constant restricts the derived list: empty in Phase A,
  `organizations` from Phase B; Phase D deletes it (and the test asserting it).
- **FR-012**: A reconciliation test MUST hold each binding's `ownerModuleId` and `table` equal to
  the entity that maps the table (`buildTableOwners`).

### Generated DDL, ledger, ordering

- **FR-020**: For each declaring module the platform MUST synthesise one migration step at the head
  of that module's block in the execution order, named
  `Migration10000101T000000<ModulePrefix>SchemaExtensions<hash12>` where `hash12` digests the
  normalised declarations; it is pending exactly when the declarations changed.
- **FR-021**: The step MUST reconcile declarations against the ledger: add missing columns/indexes
  (additive only), re-attach orphaned elements with an identical spec, mark undeclared ledger
  elements `orphaned`, refuse any non-additive change, all inside the migration transaction.
- **FR-022**: The ledger table `schema_extensions` (platform-owned, `@GlobalEntity`) MUST record per
  element: module, host table, kind, physical name, key, normalised spec, spec hash, status
  (`applied` | `orphaned` | `dropped`), platform and package versions, timestamps.
- **FR-023**: The step's `down()` (run by `uninstall --hard`) MUST mark the module's rows
  `orphaned` and drop nothing; `migrate up` MUST also mark `orphaned` the `applied` rows of a module
  that no longer has any discovered declaration (D-291 R-A5).
- **FR-024**: A declared column that already exists unledgered MUST be adopted when its type
  matches and refused otherwise.

### Verification

- **FR-025**: `migrate up`, `migrate fresh` and lifecycle `install` MUST run migrations inside one
  explicit transaction and run the verifier on it before commit; drift rolls the run back.
- **FR-026**: `composeApp` MUST run the verifier right after opening the ORM; drift fails boot with
  `SchemaExtensionDriftError` naming module, key, column, table and the last executed migration of
  the table's owning module. Orphaned or unledgered `x_*` columns are logged at `warn`, not fatal.
- **FR-027**: The verifier MUST use one `information_schema.columns` query and one `pg_indexes`
  query regardless of the number of declarations.

### ORM projection and accessor

- **FR-030**: The platform MUST build one `EntitySchema` projection per declaration mapping the host
  PK, the host tenant key when the host is `@OrgScoped`, and the declared columns; the projection
  carries the host's classification and, for `org` scope, the `org` filter on the schema itself.
- **FR-031**: `mikroOrmConfigFrom` MUST set `discovery.checkDuplicateTableNames: false` and install
  an `afterDiscovered` rule that refuses any table mapped by more than one entity unless every
  extra mapping is a platform-built projection for a validated declaration whose properties are a
  subset of {PK, tenant key, declared columns}. MikroORM's check is never disabled without it.
- **FR-032**: Projections MUST refuse INSERT and DELETE (entity hooks), and the accessor MUST be the
  only published way to reach them; the projection's entity name is not exported.
- **FR-033**: `extensionColumns(decl, em)` MUST return `{ get(id), load(ids), set(id, patch) }`:
  `load` issues one fields-limited select; `set` validates the patch with the Zod fragment, loads
  the row's declared columns, assigns and returns `{ changedFields }` (sorted keys, never values)
  for audit; writes require
  `em.isInTransaction()`; every method is gated on the declaring module's effective state.
- **FR-034**: Hard-uninstalling a host MUST mark that host's ledger rows `dropped`.

### Command hooks (dependency on spec 176)

- **FR-040**: A declaring module MAY register a spec 176 `beforeCommit` hook (`ctx.commandHooks`) on
  a host action the host declared hookable and write its columns through the accessor on the hook's
  `em`, reporting `changedFields` with `ctx.noteAuditChanges` so they land in the host Command's
  single audit entry.
- **FR-042**: The platform MUST publish `columnExtensionHook(decl, { id, on })` on `./kernel`: a
  standard hook that validates the caller's `command.extensions[<module>]` with the patch schema
  (422 `SCHEMA_EXTENSION_INPUT_INVALID`, error code declared by `_lifecycle`, translated pl + en),
  writes it and notes the changed fields.
- **FR-041**: Hooks of a module that is off are skipped (spec 176); the core write proceeds.

### Admin reads

- **FR-050**: `@endora-commerce/contracts` MUST publish `ExtensionsQuerySchema` (`extensions`:
  comma-separated module ids, max 8) and `ExtensionAttributesSchema`
  (`Record<moduleId, Record<key, json>>`).
- **FR-051**: Each extensible host's admin detail and list GET MUST accept `extensions` and, when
  given, attach `extensions` per record through the platform `schemaExtensionReads` service, with
  one query per requested module per response.
- **FR-052**: A requested module is included only when it declares that host with
  `adminReads: true` and is effectively present; otherwise it is omitted without error. Without the
  parameter, responses are unchanged.
- **FR-053**: The existing admin detail zones are the UI slot; no new zone or host component.

### Deferred, explicitly (not built, and refused where a declaration asks)

- **FR-060**: `filterable` / `sortable` flags: refused in a declaration as `not-offered-yet`.
- **FR-061**: An `extensions` field in core admin PATCH/POST **HTTP bodies**: not offered (176
  leaves it to 178; OD-178-6). Server-side callers pass `command.extensions` to hookable Commands
  (FR-042); otherwise writes go through the module's own routes and Commands.
- **FR-062**: Search index, exports, PDFs, storefront responses, events and audit of core Commands
  without a hook carry no extension data.
- **FR-063**: Composite indexes, foreign keys and non-constant defaults: refused.
- **FR-064**: Overlay modules (`backend/src/apps/`) cannot declare extensions (they ship no schema,
  D-106).
- **FR-065**: An admin screen for the ledger: not offered; the CLI lists and drops.

### Foreign schema refusal (OD-17)

- **FR-070**: Every migration of origin `external` MUST run through a platform guard that classifies
  each statement passed to `addSql` / `execute` and refuses DDL or DML on a table the module does
  not own, except `update <host> set <own x_ columns>` on a host it declares.
- **FR-071**: First-party migrations recorded in the R2 ledger
  (`backend/scripts/ledgers/migration-foreign-writes/`) are exempt by (module, class name, table),
  through a list `composer:generate` renders into `@endora-commerce/platform/migrations`.
- **FR-072**: A new static check `check:extensible-tables` (job `quality`) MUST refuse, in a
  migration of a module owning an extensible table, statements that rebuild it (`drop table`,
  `rename to`, `create table … as select … from`, `insert into … select * from`, `select *` into a
  fixed shape) and MUST hold FR-012's binding/owner reconciliation; inventory, estate entry, red
  proofs, exit 2 and read-size line per `specs/conventions/check-estate.md`.

- **FR-073**: `module:schema-extensions audit-packages` MUST run the FR-070 classification over the
  installed packages' migrations without executing them and list every would-be refusal, so an
  operator can check packages on the release before upgrading.

### Preservation, uninstall, drop

- **FR-080**: An integration test MUST apply the full migration order to a fresh database, adding
  sample `x_fixture_*` columns (nullable, defaulted NOT NULL, unique partial index) to each
  extensible table immediately after the migration that creates it, and assert all of them survive
  to the end.
- **FR-081**: `module:schema-extensions list` MUST print the ledger; `module:schema-extensions drop
  <moduleId> [--key <key>] --confirm` MUST run the audited Command `schema_extension.drop` under
  system scope, only on `orphaned` rows of a module that no longer declares them; without
  `--confirm` it prints the plan.
- **FR-082**: Uninstalling a host while a declaring module is installed MUST be refused by the
  existing `dependents-block`.

### Governance and documentation

- **FR-090**: Amend constitution I (column-granular ownership) and XV (schema surface: side tables,
  declared columns on extensible tables, owner variants; never overrides of core columns,
  constraints or entity metadata); add XIV's sentence that a developer-declared extension is not an
  operator runtime extension. Version 4.1.0 → 4.2.0 (MINOR) with Sync Impact Report.
- **FR-091**: Update `docs/docs/architecture/customisation-ladder.md` and its Polish twin: replace
  "Never a rung: schema" with a data ladder (custom fields, side table, declared columns, owner
  variants).
- **FR-092**: Update `docs/docs/architecture/migrations.md` (+ PL): the generated step, the guard
  and the column-ownership exception; `specs/conventions/module-migrations.md` (R2 exception for own
  `x_` columns); `specs/conventions/module-activation.md` (extension columns inert while off).
- **FR-093**: A developer page for S2 (EN + PL) with the worked example.

## Success Criteria *(mandatory)*

- **SC-001**: The worked example adds a column to `organizations`, writes it from a Command and
  reads it on an admin read with zero core source edits beyond FR-051's generic attach.
- **SC-002**: Core responses, inserts and audit entries are byte-identical with the example
  installed and absent (off-state test).
- **SC-003**: A core migration that loses an `x_*` column on any extensible table fails CI.
- **SC-004**: A package migration writing a foreign table cannot complete `migrate up`.
- **SC-005**: Boot verification adds ≤ 2 queries and ≤ 20 ms on a database with 9 extended tables.

## Decisions *(resolved — owner rulings of 2026-11-10, decision **D-291**)*

All architect recommendations were accepted by the owner on 2026-11-10 and are recorded as
decision **D-291** (spec 176 is D-289, spec 177 is D-290). None of them is open any more.

- **OD-178-1 — resolved: head.** The generated DDL runs at the **head** of the declaring module's
  block (research R-5): after every module it depends on, the host included, and before the
  module's own migrations, so they can back-fill the new column on a fresh database.
- **OD-178-2 — closed** on reconciliation with 176's draft: `noteAuditChanges` gives one audit
  entry with names only. Remains a dependency on 176 merging unchanged (re-checked at T046).
- **OD-178-3 — resolved: flush-time guard.** The runtime foreign-schema guard also wraps a
  migration's `getEntityManager()` with a flush-time table check rather than refusing the method.
  The design stays as written; it is built in Phase C.
- **OD-178-4 — resolved: later release.** `organizations` ships first (Phases B + C together);
  the other eight hosts (Phase D) ship in a later release and are **out of this release**. OD-15's
  list is honoured by derivation; the rollout constant is temporary.
- **OD-178-5 — resolved: opt-in.** `adminReads` defaults to `false`.
- **OD-178-6 — resolved: deferred.** No HTTP `extensions` body on core admin writes; server-side
  callers pass `command.extensions`.
- **OD-29 (restated for D-291)** — uninstalling the declaring module keeps its columns (ledger rows
  `orphaned`); an explicit audited command drops them (FR-034, FR-081).

### D-291 addendum — architect rulings on the implementation (2026-11-10, after Phases A–C)

Taken by the architect on questions the developer raised from `feat/178-extensible-columns-c`
(`8a4ca9c9d`); none reopens an owner ruling.

- **R-A1 — the stricter OD-17 guard stays.** The guard also reads function bodies
  (`create function … $$ … $$`), PL/pgSQL `execute '…'` strings and the migration entity manager's
  non-flush shortcuts (`nativeInsert`/`nativeUpdate`/`nativeDelete`, `insert`, query builders), on
  top of `addSql`/`execute`/flush. Rationale: each of those is a write path a package can take, and a
  guard that skips one is a guard with a documented bypass; the measurement (T065: every first-party
  module refuses exactly the R2 ledger's (module, migration, table) set, without exemptions, in both
  directions) shows the stricter reading produces no false refusal on the corpus we own. Narrowing
  was rejected: it would buy nothing measurable and reopen OD-178-3's hole by another door.
  `contracts/foreign-schema-guard.md` §1 is amended to the implemented scope.
- **R-A2 — own tables no entity maps are recognised by the dry run, as built.** Own = entity tables ∪
  tables the module's own migrations create and no other module's entity maps; tables created by
  earlier migrations of the module are found by an in-memory dry run of its migrations (`execute`
  answering no rows), lazily at the first guarded migration, never at boot. Its failure direction is
  **closed**: a table the dry run cannot see is treated as foreign and refused loudly, never allowed.
  Rejected: a manifest `ownedTables` declaration (a second, unverifiable claim a package could make
  about any table), and reading `mikro_orm_migrations` history (says nothing about tables).
- **R-A3 — constitution merge order.** 178 merges first and carries 4.1.0 → 4.2.0. Whichever of 177
  and 176 merges next rebases and takes the next MINOR (4.3.0), the last one 4.4.0; each Sync Impact
  Report states the version it found on `master` and chains from it. No spec reserves a version in
  advance. 178 B + C do not depend on 176 (only T046/T046a do), so 176 P1 being blocked does not hold
  178 back.
- **R-A4 — pruning stale generated-step rows is accepted, bounded.** `migrateUpVerified` may delete
  rows of `mikro_orm_migrations` only when (i) the name carries the reserved stamp
  `Migration10000101T000000` — which `orderMigrations` refuses on any non-generated entry, so no
  author can produce one — and (ii) the name is not in the current migration list; inside the same
  transaction as `up` and the verifier; each pruned name logged at `info`. Rationale: the step's name
  is a digest, so A → B → A must re-run A's reconcile, and the rows pruned are already ignored by
  umzug. Rejected: a generation counter in the name (not a pure function of the declarations, so
  fresh and upgraded databases diverge) and reconciling outside the migration list (loses ordering,
  lock and history). The developer adds a test that no other row is ever touched (T068).
- **R-A5 — OD-29 orphan marking is fixed in this release.** At migrate, `migrateUpVerified` marks
  `orphaned`, inside its transaction, every `applied` ledger row whose module has **no discovered
  declaration at all** (package removed without `uninstall --hard`). Without it the drop command —
  which acts only on `orphaned` rows — could never clean up after a vanished package, which is the
  OD-29 promise unkept. It is non-destructive and reversible (a returning package re-attaches the
  rows, same hash → `applied`). A module that still declares something is left to its generated step;
  boot stays read-only and only warns (FR-026). Task T069; blocks the release with B + C.
