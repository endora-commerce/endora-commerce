**A package migration that writes another module's table now fails `migrate`** (`specs/178-extensible-columns/` FR-070, OD-17). Every migration of an installed package (origin `external`) runs inside a foreign-schema guard: each statement it hands to `addSql` or `execute` — knex builders by their rendered SQL, `do $$ … $$` blocks, function bodies and PL/pgSQL `execute` strings by their text — and every write through `getEntityManager()` (flush change sets, `insert*`, `upsert*`, `native*`, `execute`) is classified, and DDL or DML on a table the package's module does not own is refused with `ForeignSchemaWriteError` (`foreign-schema-write`, naming package, migration, table and statement); the whole run rolls back. Allowed: the module's own tables (mapped by its entities, or created by its migrations and mapped by no other module's entity), the platform's tables, DDL on a table the same migration creates, `update <host> set <own x_<module>_ columns>` on a host the module declares extension columns on, and the first-party R2 writes in `FIRST_PARTY_FOREIGN_WRITE_EXEMPTIONS` (new on `./migrations`, generated from `check:module-boundary`'s ledger) — so an instance installing this platform's own modules migrates as before.

**Before upgrading**, run `module:schema-extensions audit-packages` (new verb, `runSchemaExtensionsCommand`): it applies the same classification to every installed package's migrations without executing them, lists each statement that would be refused and exits 65 when there is one. `./db` publishes `sqlWriteTargets`, `guardExternalMigration`, `dryRunStatements`, `auditForeignSchemaWrites` and `ForeignSchemaWriteError`; `configuredMigrationsFrom` accepts `foreignWriteExemptions`.
