The buyer's order actions are judged by what they build (`specs/170-organization-roles/`, WP-16). `POST /api/v1/orders/:id/reorder` replaces the active basket and now refuses a member whose organization role lacks `carts.create` with `403 ORGANIZATION_PERMISSION_REQUIRED` (`details.permission = 'carts.create'`); `POST /api/v1/orders/:id/clone-to-quote` creates a quote request and now refuses a member lacking `quote_requests.create` the same way. Both refusals come after `requireCustomer` and before the order is read, so the answer is the same for the member's own order, a colleague's and an unknown id; a member holding the code then meets the order scope as before (`404 ORDER_NOT_FOUND` for a colleague's order without `orders.view_organization`). While `quote_requests` is switched off, its code grants nothing, so the buyer's clone is refused by the guard (`403`) instead of the service's `503 MODULE_DISABLED` (owner ruling of 2026-11-04). The operator routes `POST /api/v1/admin/orders/:id/{reorder,clone-to-quote}` are unchanged. The three `ORDER_CART_APPROVAL_REQUIRED` sentences (`cart_approval_not_submitted`, `cart_approval_pending`, `cart_approval_rejected`) now say that the member's role requires approval and that an approver in the organization decides, not the organization administrator. No member loses access on upgrade, because *Member* and *Administrator* hold both codes.
