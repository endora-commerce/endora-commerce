**`organizationCommandPort` — every server-side write on an Organization** (issue #1821, `specs/186-aggregate-ports/` US1). Another module, an overlay or an integration worker creates, updates, places in the tree, approves, rejects, blocks, unblocks and deletes an Organization, sets its custom-field values, sales channels, allow-lists, credit-inheritance mode and sales representatives through the published port, with the ambient actor (the system actor under `withSystemScope`) and an optional `source` code recorded in the audit entry. Each method runs the Command its admin endpoint runs, with the same refusals; `create` and `setSalesChannels` answer an unknown sales channel `422 UNKNOWN_SALES_CHANNEL` as `organizationWritePort.create` always has. `organizationWritePort` and `organizationCustomFieldWritePort` are deprecated and delegate to it, writing the same entries as before.

The allow-list writes (`organization.allow_lists_replace`, `organization.allow_list_patch`) and the sales-representative assignment (`organization.sales_rep_assign`, `organization.sales_rep_unassign`) are now Commands: the change and its audit entry commit together, command hooks can see them, and the action strings and audit state are unchanged. Assigning a representative already assigned records nothing, as before. Two changes on the published `organizationSalesRepScopePort.assign`: called without `assignedByAdminUserId` it now records the ambient administrator (it recorded `null`), and an unknown Organization is now refused `404` instead of failing in the database. The allow-list and sales-representative endpoints keep their requests, responses and audit entries.

Replacing an Organization's sales channels (`PUT /api/v1/admin/organizations/:id/sales-channels`, `organizationCommandPort.setSalesChannels`) is now the Command `organization.sales_channels.set`. Besides the one `sales_channel.membership.changed` entry per channel added or removed, which are kept and now commit in the same transaction, it records one `organization` entry with the channel ids before and after; the same set again still records nothing. The endpoint's request, status codes and response are unchanged; the extra `organization` audit entry is the one change it makes.

The customer's approval and rejection e-mails are now sent by this module's subscriber of `organization.status_changed.v1`, after the change commits, so they also go out when an approval runs inside another Command. The event gains `notifyCustomer: boolean` (`false` for a rejection with `notifyCustomerEmail: false`, and for a block or unblock).

For code that builds the services by hand: `OrganizationRestrictionService` and `SalesRepAssignmentService` take the Command Bus as their second constructor argument, in place of the audit port; `OrganizationWriteService` takes `{ commands, lookup }` and `OrganizationCustomFieldWriteService` the aggregate port; `OrganizationModerationService.approve` / `reject` / `block` / `unblock` take `expectedVersion` as optional, and no longer send the notice themselves — subscribe `notifyStatusChanged` to the event to send it.
