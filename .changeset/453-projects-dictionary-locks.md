Projects dictionaries no longer race (issue #453). Two creates of one default name on `/api/v1/admin/projects/roles` or `…/loss-reasons` arriving at the same moment collided on the code's unique index (reported in the issue as a `500`, answered today as `409` `VERSION_CONFLICT`) instead of answering `PROJECT_DICTIONARY_NAME_TAKEN`; a create now takes the dictionary's advisory lock inside its Command before it checks the name, picks the code and reads the next position (a rename takes it before its name check), so the second create answers `409` `PROJECT_DICTIONARY_NAME_TAKEN` and no `_2` row is written. A Role delete could also commit while a Stage save stored that Role's id in `responsible_role_ids`, which has no foreign key; the delete now takes the Role's lock exclusively before asking whether it is in use, and every Stage, Stage Task, Template and new-Project write that names Roles takes each one's lock shared, in sorted order, and checks again inside it that each still exists (`422` `VALIDATION_FAILED` if not). Stage saves share the lock and do not wait for each other.
