Declared command middleware on the Command Bus (`specs/189-command-middleware/`, issue #1840). A module declares `commandMiddleware` in its manifest and registers the code with the new `ctx.commandMiddleware([{ id, phase: 'admit', admit }, { id, phase: 'observe', observe }])`. The bus runs every present, matching `admit` before a Command does anything — the root before its transaction opens, and every child Command, hook-started ones included, at entry — with metadata only (`CommandAdmissionMeta`: action, object, actor, organisation, request metadata, lineage). An `admit` refuses by throwing `CommandRefusedError` with a code its module declares; a timeout or any other throw refuses with `503 COMMAND_ADMISSION_TIMEOUT` / `COMMAND_ADMISSION_FAILED`. `module.activation.set` is never admitted. After the run commits, rolls back or is refused, each present, matching `observe` receives a names-only `CommandRunOutcome`, detached from the caller, budgeted and capped in flight; an installed package's observer gets the request id and no IP address or user agent. A middleware calling `CommandBus.run` is refused with `500 COMMAND_MIDDLEWARE_REENTRY`. Switching a module off skips its middleware on the next Command. An installed package may contribute `observe` only (`CommandMiddlewareOriginError`). Two overlapping `admit` middlewares from modules no dependency orders refuse composition unless the deployment's `divergence.ts` declares `commandMiddlewareOrder`. With no middleware composed the bus behaves exactly as before.

New on `./commands`: `CommandRefusedError`, the handler and outcome types, the composition refusals and `currentCommandMiddlewareOrigin`. New on `./composition`: `CommandMiddlewareRegistry` and `commandMiddlewareFrom`; `ComposeAppOptions` gains `commandMiddlewareOrder`, and `composeApp` builds the registry and passes it to the bus and to `composeModules`. `ModuleEntry` gains `origin` and `installedPackageName`, stamped by the overlay and package loaders: an installed package is `core` only when its own package name and module id are one of this release's first-party module packages (the new generated `FIRST_PARTY_MODULE_PACKAGES`), and `package` otherwise. The boot log gains one `kernel.command-middleware` line when any middleware is composed.
