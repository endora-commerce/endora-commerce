A storefront that is alive but no longer answering is now restarted (issue #152). `endora new storefront` writes a `Dockerfile` whose command is a supervising parent, `scripts/supervise.mjs` (part of the scaffolded tree): `CMD ["node", "storefront/scripts/supervise.mjs", "storefront/server.js"]` replaces `CMD ["node", "storefront/server.js"]`. The supervisor runs the standalone server as its child, forwards `SIGTERM`/`SIGINT`/`SIGHUP` and the child's exit code, probes `http://127.0.0.1:$PORT/robots.txt`, and after three consecutive unanswered probes sends `SIGTERM`, then `SIGKILL`, and exits `1` so the restart policy starts a fresh container. Any HTTP status counts as an answer. It is tuned or switched off with the optional `STOREFRONT_SUPERVISOR_PROBE`, `_PROBE_URL`, `_INTERVAL_SECONDS`, `_TIMEOUT_SECONDS`, `_FAILURES`, `_START_GRACE_SECONDS` and `_KILL_GRACE_SECONDS` variables; an unreadable value stops the container at start. The `storefront` service in the instance's compose examples (`deploy/compose.prod.yml` and `deploy/three-host/compose.storefront.yml`) now sets `init: true`. An existing storefront picks this up by copying `scripts/supervise.mjs` and the Dockerfile's last stage; nothing else changes.
